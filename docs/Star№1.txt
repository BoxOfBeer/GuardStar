GuardStar — быстрый аудит проекта (2026-04-28)
===========================================

Что уже хорошо
--------------
1) Есть рабочий MVP backend на Flask + PostgreSQL.
2) Есть миграции Alembic.
3) Есть базовые автотесты на auth + карту мира.
4) Присутствует разделение на service/db/routes, что упрощает рост проекта.


Что, на мой взгляд, сейчас не хватает
------------------------------------

[Критично]
1) Нет server/.env.example
   - В README есть ссылка на этот файл, но в репозитории его нет.
   - Это ломает «быстрый старт» для нового разработчика.

2) Нет фиксированного процесса запуска тестов в изолированной среде
   - Тесты завязаны на реальную PostgreSQL через DATABASE_URL/TEST_DATABASE_URL.
   - Нужен понятный путь: либо отдельный docker-compose для тестов,
     либо testcontainer/скрипт make test.

3) Нет CI (минимум: lint + tests)
   - Риск регрессий при любом изменении API/моделей.


[Важно]
4) Секреты имеют опасные default-значения в Config
   - Для dev это нормально, но нужен guard для prod:
     если FLASK_ENV=production и SECRET_KEY/SERVER_SALT дефолтные — падать при старте.

5) Нет API-контракта
   - Нужен хотя бы минимальный OpenAPI/Swagger или markdown со схемами
     /api/register, /api/login, /api/me, /api/world/window, /api/units/move_scout.

6) Нет централизованной валидации входных данных
   - Сейчас проверки размазаны по route handlers.
   - Рекомендуется ввести pydantic/schemas для request/response.

7) Нет rate-limit на auth endpoints
   - /api/login и /api/register уязвимы к brute-force/спаму.


[Желательно]
8) Не хватает наблюдаемости
   - Нет structured logging (request id, player id, duration, status).
   - Нет health/readiness endpoints для деплоя.

9) Не хватает формальной стратегии версионирования API
   - Сейчас есть /api/version, но нет /api/v1/... маршрутов.

10) Не хватает тестов на негативные сценарии
    - radius<1/radius>10, z outside limits, invalid payload types,
      idempotency поведения и ошибки доменной логики.


Предлагаемый порядок исправлений (прагматично)
----------------------------------------------
Шаг 1 (быстро, 1 день):
- Добавить server/.env.example.
- Добавить Makefile/скрипты: run, test, lint, migrate.
- Подключить CI (GitHub Actions): pytest + ruff/flake8.

Шаг 2 (1-2 дня):
- Добавить production guard для SECRET_KEY/SERVER_SALT.
- Добавить rate limiting для auth endpoint'ов.
- Вынести валидацию payload в отдельные схемы.

Шаг 3 (2-3 дня):
- Описать OpenAPI и зафиксировать контракты.
- Добавить health/readiness и нормальные логи.
- Расширить тесты на boundary/error cases.


Мини-чеклист готовности к следующему этапу
------------------------------------------
[ ] Новый разработчик поднимает проект «с нуля» за 10-15 минут по README.
[ ] CI запускается автоматически на PR.
[ ] Ошибки API документированы и стабильны.
[ ] Prod-конфигурация не стартует с дефолтными секретами.
[ ] Тесты покрывают базовые edge-cases по world/auth.
